# Robot strategy research brief (Junction 2026, Rokoko track)

Written 2026-11-14 during the event. Every web claim has a link. Items marked UNVERIFIED are inference or could not be confirmed.

## Recommendation (read this first)

1. Do not buy into a hardware story. Build a browser digital twin of the Dex3-1 (urdf-loaders, kinematic, driven by the existing websocket). It costs about 2 to 4 hours, runs on Windows, and looks good on a projector.
2. Frame the robot as a **second learner scored by the same scorer**, plus a **data export** (expert glove recordings become robot demonstrations). Both framings are backed by Rokoko's own marketing and by published work. Do not claim the robot teaches humans better than the 3D ghost hand: the literature does not support that.
3. Show honest limits live: a "can the 3-finger hand form this?" feasibility score per skill. Judges at robotics tracks reward candour about embodiment gaps, and it protects you from overclaiming.
4. Optional extra, only if time remains: MuJoCo (Python, `pip install mujoco`) for a grasp-a-ball clip. Skip Isaac Sim on Windows.

## 2. Simulation options, ranked

Dex3-1 facts: 7 DoF (thumb 3, index 2, middle 2), 710 g, official URDF `dex3_1.urdf` and STEP file ([Unitree docs](https://support.unitree.com/home/en/dex3-1_hand/about_dex3-1)). Joint order and URDF names: [Unitree G1 developer docs](https://support.unitree.com/home/en/G1_developer/dexterous_hand). Unitree's `unitree_ros` repo ships Dex3-1 URDF, with left and right ([robots README](https://github.com/unitreerobotics/unitree_ros/blob/master/robots/README.md)).

| Rank | Option | Dex3-1 model? | Contact physics | 60 Hz Python websocket | Windows effort | On stage |
|---|---|---|---|---|---|---|
| 1 | three.js + urdf-loader | Yes, URDF + meshes (you already have URDFs) | None (kinematic only) | Trivial, `joints[name].setJointValue(q)` per frame | Low, 2 to 4 h, `npm i urdf-loader` | Good: crisp, shareable, runs in the app itself |
| 2 | MuJoCo Python (`pip install mujoco`) | Dex3 inside LeRobot's G1 MJCF on Hugging Face (not in Menagerie) | Yes | Yes, step at 500 Hz, apply targets at 60 Hz | Low to medium, 3 to 6 h to tune the hand | Very good if a ball is grasped |
| 3 | MuJoCo WASM in browser | Same MJCF via virtual file system | Yes | Yes, in-page | Medium to high | Great but risky |
| 4 | PyBullet | Via URDF | Yes, but fiddly | Yes | Low | Dated look |
| 5 | Unitree sim / Isaac Lab | Yes (G1 + Dex3 tasks) | Yes | DDS, not websocket | High, needs RTX GPU, Linux-first | Impressive, but too heavy for 1 to 2 days |

Evidence per row:
- **urdf-loader** (gkjohnson): loads URDF into three.js, `load`, `loadAsync`, `parse`, supports `packages` mapping for `package://` mesh paths ([npm](https://www.npmjs.com/package/urdf-loader), [docs](https://gkjohnson.github.io/tools/docs/urdf-loader/URDFLoader)). Joint setting API is `robot.setJointValue(name, value)` per the project README (I did not fetch that part; UNVERIFIED line-level). Gotchas: left and right Dex3 hands differ in rotation direction ([Classmethod article, Japanese](https://dev.classmethod.jp/articles/unitree-g1-dex3-hand-isaac-sim)), and the IDL order (thumb 0 to 2, middle, index) differs from the URDF names (`left_hand_zero`... see Unitree table above). Map by name, not index.
- **MuJoCo Menagerie** has no Dex3-1. It has Shadow Hand, LEAP Hand (16 DoF), Allegro, Shadow DEX-EE, Sharpa Wave and Unitree G1 (29 DoF, no hands in the list) ([Menagerie](https://github.com/google-deepmind/mujoco_menagerie)). The Dex3 MJCF lives in `lerobot/unitree-g1-mujoco` (`END_EFFECTOR: dex3`, 7 joints per hand, meshes included) ([Hugging Face](https://huggingface.co/lerobot/unitree-g1-mujoco)). Extract the hand subtree to avoid simulating the whole humanoid.
- **MuJoCo WASM**: official `@mujoco/mujoco` npm package; README warns Windows support "remains experimental (installation succeeded on one Windows 11 machine but failed on others)" ([README](https://github.com/google-deepmind/mujoco/blob/main/wasm/README.md)). Lower-risk browser route: run MuJoCo in Python and stream state, or use `mjviser`, a web viewer for MuJoCo ([mjviser](https://github.com/mujocolab/mjviser)). Or drop an MJCF onto [live.mujoco.org](https://mujoco.readthedocs.io/en/latest/studio/web_viewers.html) for a zero-code sanity check.
- **Isaac / Unitree sim**: `unitree_sim_isaaclab` has Dex3 pick-and-place tasks and uses the same DDS topics as the real robot; tested on RTX 3080 to 4090 ([repo](https://github.com/unitreerobotics/unitree_sim_isaaclab)). Rokoko's own Isaac Lab example exists but needs the licensed SDK and Isaac Lab 2.3 on Isaac Sim 5.1 ([insight](https://www.rokoko.com/insights/rokoko-sdk-now-supports-nvidia-isaac-lab)). I found no evidence Windows is a first-class path (UNVERIFIED). Skip.
- **Real-robot DDS contract**, if hardware does appear: topics `rt/dex3/left|right/cmd` and `/state` with `HandCmd_` of 7 `MotorCmd_` ([docs](https://support.unitree.com/home/en/G1_developer/dexterous_hand)). Keep your websocket message shaped like this so a bridge is a 30-line script.

## 3. Credible framings for a skill-learning product

Ranked from strongest to weakest evidence.

1. **Expert recordings double as robot demonstrations (strong).** DexCap trained dexterous policies from glove mocap with fingertip IK retargeting ([paper](https://arxiv.org/html/2403.07788), [site](https://dex-cap.github.io/)); Rokoko markets exactly this ([robotics page](https://www.rokoko.com/use-cases/robotics)). HumDex shows human-only data improves policy generalisation ([arXiv](https://arxiv.org/html/2603.12260v1)). Pitch: "every lesson an expert records is also a labelled robot demonstration". Be explicit that you ship the export and the retarget, not a trained policy.
2. **Human and robot as two learners, one scorer (strong, novel, cheap).** Score the retargeted robot trajectory with the same per-finger scorer. The robot "fails" thumb abduction on a 3-finger hand, which shows the scorer is embodiment-aware. This is your own idea; no source says it is established. Label it as a design choice.
3. **Apprentice teleoperates the robot to prove mastery (credible as a test).** Teleop operator skill measurably improves with practice: control reliability 73.5% to 99.3% in one session ([Rokoko case study](https://www.rokoko.com/insights/collecting-robot-training-data-with-rokoko-smartgloves)). Framing: "passing the lesson = completing a task through the robot". Needs hardware or sim contact physics to be convincing, so it is a stretch goal.
4. **Robot as exoskeleton or physical demonstrator for humans (real research, but mixed).**
   - Positive: expert pianists trained passively by a hand exoskeleton at speeds beyond voluntary ability played faster ([Science Robotics 2025](https://www.science.org/doi/10.1126/scirobotics.adn3802)). Novice violin bowing improved with an exoskeleton, N=12 per group, authors call it a pilot ([Sci Reports 2026](https://www.nature.com/articles/s41598-026-39226-8)). Golf pitch wrist timing shaped by robotic guidance and retained at 7 days ([Hum Mov Sci 2014](https://www.sciencedirect.com/science/article/abs/pii/S0167945714001250)).
   - Negative: for spatial paths, haptic guidance gave no advantage over just watching, and trended worse ([Reinkensmeyer, PMC review](https://pmc.ncbi.nlm.nih.gov/articles/PMC2905644), [JNER 2006](https://link.springer.com/article/10.1186/1743-0003-3-20)); a 2015 review says haptic demonstration is "inferior to visual demonstration for movement paths" ([Heuer and Luttgen](https://www.sciencedirect.com/science/article/abs/pii/S0149763415001906)).
   - Implication: a free-standing 3-finger robot hand next to a screen adds no proven learning benefit over your 3D ghost hand. Do not claim it does. A wearable exoskeleton is a different thing and out of scope.
5. **Retargeting quality as a metric (useful, cheap).** Papers evaluate retargeting by success rate and calibration sensitivity (AnyDexRT, [arXiv](https://arxiv.org/html/2607.08341); HumDex learned vs optimisation retargeting, [arXiv](https://arxiv.org/html/2603.12260v1)). For you: report fingertip-distance error between human and robot hand, per finger, after retargeting. Fits the "same scorer" story. UNVERIFIED that any standard benchmark exists for 3-finger hands.

Related systems to name-drop correctly: AnyTeleop (vision-based, URDF-only adaptation, browser viewer, [arXiv](https://arxiv.org/html/2307.04577)); Open-TeleVision (immersive stereo feedback, [PMLR](https://proceedings.mlr.press/v270/cheng25b.html)); Bunny-VisionPro (bimanual, haptic feedback to operator, [IEEE](https://ieeexplore.ieee.org/document/11247017)); HATO (30 min to 2 h of teleop data gave policies, multifingered hands beat parallel grippers for teleop, [arXiv](https://arxiv.org/html/2404.16823v2)). Note most use vision or XR; Rokoko's selling point over them is IMU gloves with no occlusion ([Rokoko Isaac Lab post](https://www.rokoko.com/insights/rokoko-sdk-now-supports-nvidia-isaac-lab)).

## 4. Wow factor and demo ideas

**Patterns with evidence:** I found no source on what wins robotics hackathons, so the following are design judgements (UNVERIFIED as "what judges reward"). The nearest evidence: the Rokoko case study itself earns trust by listing failures ([insight](https://www.rokoko.com/insights/collecting-robot-training-data-with-rokoko-smartgloves)), and Tutor Intelligence reports that a ghost robot mirroring state plus vibration on grasp reduced mistakes and demo times ([PDF](https://its-the-demos.github.io/abstracts/camera_ready/6_Maintaining_Demonstration_Quality_in_a_100_Robot_Teleoperation_Pipeline.pdf)). Their latency target: point-cloud update under 50 ms (same PDF). Use 50 ms end to end as your own stated budget.

**Demo shot list (3 minutes):**
1. Split screen, live: expert ghost hand (3D), learner's real glove hand, robot Dex3 twin. Three hands, one score bar each.
2. Show a latency readout on screen (glove timestamp to render). Be honest: if it is 80 ms, say 80 ms.
3. Cut to the "Robot feasibility" panel for the lesson, see below.
4. Show the export: click "Export as robot demonstration" and show the file (joint targets at 60 Hz, Dex3 joint order). Say "this is what DexCap-style training consumes", not "we trained a policy".
5. Close with one deliberate failure: robot cannot do a letter, scorer shows the thumb or ring finger as unreachable. Then show the human still gets fully scored.

**Per skill, within 3 fingers (inference from the joint list, UNVERIFIED on hardware):** Dex3 has thumb, index, middle only, with spread DoF on thumb and flexion-only fingers (joint ranges in [Unitree specs](https://www.unitree.com/Dex3-1)). So index and middle have no abduction joint.
- **Table tennis grip:** good fit. Shakehand and penhold are thumb-index dominated; a Dex3 can hold a paddle handle in sim. Best "robot completes what the human taught" candidate if you add a rigid paddle in MuJoCo. Only the hold, not the stroke.
- **Finnish fingerspelling:** partial. Letters that need ring or little finger, or finger crossing, are out. Letters using thumb, index, middle (point, V shape, closed fist, O ring with thumb and index) are plausible. I did not verify the Finnish handshape chart; build the table from your own `moves.json`. Show a letter coverage bar, e.g. "robot can form N of M letters", computed rather than asserted.
- **Piano:** one finger at a time is fine for pressing a key if the wrist moves; fixed hand cannot span an octave. Use a sim key press for a single-finger exercise only; do not claim chords.
- **Shadow puppets with a lamp:** the best visual. The projected shadow is the output, so the 3-finger hand can make a "bird" or "dog" with a different silhouette. Treat the shadow outline as the scorer target (silhouette IoU) rather than joint angles: it is embodiment-independent, which is a strong way to compare human and robot. This is a design idea, not sourced.

## 5. Pitfalls

- **Latency.** The glove stream is up to 83 Hz per glove per Rokoko's ROBOTIS page ([source](https://www.rokoko.com/robotics/robotis-hand)), so a 60 Hz render loop is fine, but WiFi, JSON, and websocket buffering add jitter. Timestamp each frame, drop stale frames, never queue. Rokoko's glove link is TCP ([Smartgloves II page](https://www.rokoko.com/products/smartgloves-ii)), so bursts are possible.
- **5 to 3 finger retargeting.** Three published approaches: fingertip IK as in DexCap ([arXiv](https://arxiv.org/html/2403.07788)), a learned MLP trained on 20 minutes of paired data in HumDex ([arXiv](https://arxiv.org/html/2603.12260v1)), and mapping fingers to motors (YAAK five fingers to six motors, [insight](https://www.rokoko.com/insights/collecting-robot-training-data-with-rokoko-smartgloves)). The cheapest for you: map thumb to thumb, index to index, middle to middle, merge ring and little into middle for grip strength, log what was dropped. Calibration matters: AnyDexRT found baselines degrade sharply under glove-to-robot frame misalignment ([arXiv](https://arxiv.org/html/2607.08341)); do a flat-hand and fist calibration step on stage.
- **Safety.** If real hardware appears: Dex3 peak 10 A, 400 W for 3 s, 500 g grasp ([Unitree specs](https://www.unitree.com/Dex3-1)). Clamp joint limits (ranges are on the same page), rate-limit velocity, and add a watchdog that holds position when frames stop. Use a deadman key. A thumb motor failed in YAAK's rig ([insight](https://www.rokoko.com/insights/collecting-robot-training-data-with-rokoko-smartgloves)).
- **Overclaiming.** Do not say: "robot teaches humans" (evidence is mixed, section 3), "trained a policy" (you did not), "works on a real Dex3" (you did not test), "fingerspelling the full alphabet" (3 fingers cannot). Say: "digital twin", "retargeted trajectory", "robot-ready demonstration export", "same scorer for both embodiments". Mark simulated clips as simulated on screen.
- **Windows tooling.** MuJoCo WASM is experimental on Windows ([README](https://github.com/google-deepmind/mujoco/blob/main/wasm/README.md)); use Python MuJoCo or three.js.
- **Licence check.** Unitree URDF meshes: I did not verify licence terms. Menagerie G1 is BSD-3 ([Menagerie](https://github.com/google-deepmind/mujoco_menagerie)). Submissions are MIT, so check before committing meshes.
